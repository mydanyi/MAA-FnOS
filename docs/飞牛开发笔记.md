# 飞牛 fnOS 开发笔记

做这个项目时踩过的飞牛平台坑，以及验证过的机制。**给未来的自己和后来的开发者省时间。**

官方文档：<https://developer.fnnas.com/docs/guide/>

## 1. fpk 应用结构

```
myapp/
├── app/                      # → 安装后摊平到 ${TRIM_APPDEST} (/vol1/@appcenter/<appname>)
│   ├── ui/
│   │   ├── config            # 桌面入口 JSON
│   │   └── images/           # 桌面图标 icon_<size>.png + icon_{0}.png
│   ├── <运行文件>             # 如离线镜像、辅助脚本
│   └── docker/               # 只有 docker 模板才有
├── cmd/
│   ├── main                  # start / stop / status
│   ├── install_init  / install_callback
│   ├── upgrade_init  / upgrade_callback
│   ├── uninstall_init / uninstall_callback
│   └── config_init   / config_callback
├── config/
│   ├── privilege             # JSON，运行身份
│   └── resource              # JSON，共享目录声明
├── wizard/                   # 安装/卸载/升级/配置向导（可选）
├── manifest                  # INI 元信息
├── ICON.PNG                  # 64x64  ← fnpack 强制校验
└── ICON_256.PNG              # 256x256 ← fnpack 强制校验
```

`*_init` 在动作**之前**执行，`*_callback` 在动作**之后**执行。

## 2. manifest 必填字段

```ini
appname               = maa-web
version               = 1.0.2
display_name          = MAA
desc                  = 基于 MaaAssistantArknights 官方核心的网页控制台
platform              = x86                  ; x86 / arm / all
source                = thirdparty
maintainer            = <你的名字>
distributor           = <分发者>
desktop_uidir         = ui                   ; 声明后 app/ui/ 必须存在
desktop_applaunchname = maa-web.Application  ; 对应 ui/config 里的 key
ctl_stop              = true                 ; 应用中心可停止
os_min_version        = 1.1.3100
changelog             = 1.0.2: xxx; 1.0.1: yyy
```

其余可选：`checkport`（安装时校验端口占用）、`service_port`。

## 3. 环境变量（框架注入）

| 变量 | 含义 |
|---|---|
| `TRIM_APPDEST` | 应用文件目录，`/vol1/@appcenter/<appname>` |
| `TRIM_PKGVAR` | 应用数据目录，`/vol1/@appdata/<appname>` |
| `TRIM_TEMP_LOGFILE` | **写到这里的内容会显示在应用中心界面**，用来向用户报错 |
| `TRIM_PKGTMP` | 临时目录 |
| `FNNAS_GATEWAY_SOCKET` | 统一网关要求的 Unix Socket 绝对路径（仅声明网关时） |
| `FNNAS_GATEWAY_PREFIX` | 网关路径前缀（仅声明网关时） |

**报错的正确姿势**：

```bash
write_user_error() {
    echo "$1" > "${TRIM_TEMP_LOGFILE}"     # 用户能在应用中心看到
    log_msg "ERROR: $1"                     # 同时落日志
}
```

## 4. 目录软链结构

`/var/apps/<appname>/` 下是一堆指向真实位置的软链：

```
/var/apps/maa-web/
├── target -> /vol1/@appcenter/maa-web     # = TRIM_APPDEST
├── var    -> /vol1/@appdata/maa-web       # = TRIM_PKGVAR
├── etc    -> /vol1/@appconf/maa-web
├── home   -> /vol1/@apphome/maa-web
├── meta   -> /vol1/@appmeta/maa-web
├── tmp    -> /vol1/@apptemp/maa-web
├── manifest / ICON.PNG / ICON_256.PNG / cmd/ / config/ / shares/ / wizard/
```

> `/var/apps/<app>/target/...` 是**稳定路径**，写配置/文档时优先用它，比 `/vol1/@appcenter/...` 更通用。

## 5. 桌面图标机制（容易白干半天）

1. **桌面图标**路径由数据库 `appcenter.app_service` 表的 `icon` 字段决定，默认 `ui/images/icon_{0}.png`。
   - `{0}` 是**尺寸占位符**，系统替换为 `64` / `256`
   - 实际文件用**下划线**：`icon_16.png`、`icon_32.png`、`icon_64.png` …
   - 建议补齐全系列：16/24/32/48/64/72/96/128/144/256/512 + 一个字面量 `icon_{0}.png`
   - 参考官方应用「迅雷」：9 个文件全是同一张图复制（字节数相同），一样可用
2. **应用中心图标**：包根 `ICON.PNG`(64) + `ICON_256.PNG`(256)，**文件名必须全大写**
3. **图标不显示时的排查顺序**：
   - `ls -la /vol1/@appcenter/<app>/ui/images/` 确认文件在、命名对
   - **把文件拉回本地实际打开看内容**（最有效，别猜）
   - 查库：`sudo -u postgres psql -d appcenter -x -c "SELECT * FROM app_service;"`
   - **让用户清浏览器缓存 / 换无痕窗口** ← 十有八九是这个

> 我们真的被最后一条坑了很久：NAS 上的图标文件完全正确，但浏览器缓存着旧图。

## 6. 桌面入口 `app/ui/config`

**`type` 决定点击图标后怎么打开：**

| type | 行为 |
|---|---|
| `url` | **浏览器新开页签**：`{protocol}://{当前浏览器 hostname}:{port}{url}` |
| `iframe` | **飞牛桌面内嵌窗口**（走统一网关） |

### 方式 1：走统一网关（ScrcpyNas / DeepSeekHarness 都用这种）

```json
{
  ".url": {
    "myapp.Application": {
      "title": "MyApp",
      "icon": "images/icon_{0}.png",
      "type": "iframe",
      "gatewaySocket": "myapp.sock",
      "gatewayPrefix": "/app/myapp",
      "url": "/app/myapp",
      "allUsers": false,
      "control": { "accessPerm": "readonly" }
    }
  }
}
```

- 应用必须把服务监听在 **Unix Socket**：实际路径 `${TRIM_APPDEST}/myapp.sock`
- nginx 侧由 `location /app/` → `unix:/var/run/trim_http_cgi.socket` 承接
  （见 `/usr/trim/nginx/conf/conf.d/trim_http_cgi.conf`），**已自动转发 WebSocket Upgrade 头**
- ⚠️ **前缀陷阱**：请求会带着 `/app/myapp` 进来。应用若用绝对路径引资源（`/styles/x.css`、
  `fetch('/api/...')`）就会 404（浏览器按飞牛根路径解析）。必须二选一：
  - 应用自己支持 base path / `X-Forwarded-Prefix`
  - 或在 socket 前放一个**重写代理**：入站剥前缀 + 出站给 HTML/CSS/JS 里的绝对 URL 补前缀 +
    注入 shim 兜住 `fetch`/`XMLHttpRequest`/`WebSocket` + 转发 WS

### 方式 2：iframe 直接指端口

```json
{ "type": "iframe", "protocol": "http", "port": "18000", "url": "/" }
```

iframe 的 src 成为 `http://{host}:18000/`，应用自己的绝对路径**天然正确，不需要任何重写**。
⚠️ 未在官方文档明确；且用户若走 HTTPS 访问飞牛，http iframe 会被判混合内容拦截。

> 本项目当前用的是 `type: url`（新开页签）。要改成桌面内窗口见 `BUGS.md` #8。

### 查证手段（别猜，直接查库）

```bash
sudo -u postgres psql -d appcenter -x -c \
  "SELECT service_name,type,url,gateway_socket,gateway_prefix,control FROM app_service;"
```

`app_service` 列：`service_name / title / desc / icon / type / url / default_url / is_admin /
control / full_url / no_display / file_types / gateway_socket / gateway_prefix`。

## 7. 常用命令

```bash
fnpack build                                  # 在当前目录打包
fnpack build --directory <path>

sudo appcenter-cli install-fpk --volume 1 /path/to/app.fpk   # 必须指定 --volume
sudo appcenter-cli start   <appname>
sudo appcenter-cli stop    <appname>
sudo appcenter-cli uninstall <appname>
sudo appcenter-cli status  <appname>          # 返回 0 = running
sudo appcenter-cli install-local              # 本地开发调试
```

`sudo` 需要密码时，标准输入是密码通道；脚本里用 `sudo -S -p ""` 可抑制 `[sudo] password` 提示
（这行提示会挤占 stdout，导致管道里的 `grep -v` 之类误判）。

## 8. 血泪坑位

### 坑 1：升级 fpk 必须递增 manifest version

`install-fpk` 检测到**同版本已安装会跳过文件覆盖**，你的新文件根本不生效。
→ 每次改动都要递增 `version`（1.0.0 → 1.0.1 → …）

### 坑 2：`docker load` 不会顶掉同名同 tag 的旧镜像

包内镜像更新了，但宿主机上旧镜像的 tag 还在 → 若 `ensure_image()` 只判断「镜像是否存在」
就会直接跳过 load，**新镜像永远不导入**，容器一直跑老版本。
→ 用**镜像指纹比对**，详见 `fnos-app/cmd/main` 里的 `image_ready()` / `record_image_id()`。

### 坑 3：容器名别用开发期命名

`cmd/main` 里的 `CONTAINER=` 是**线上容器名**，会常驻在用户 NAS 上。
开发期叫 `xxx-test` 打包前忘了改，用户 `docker ps` 看到会合理怀疑你偷放了测试环境 —— 这是信任问题。
→ 改名要**连带迁移**：新名字的 `stop_process` 不会清理旧名字的容器，
   需要在 `install_callback` 或首次 `start` 里加一次性 `docker rm -f <旧名>`。

### 坑 4：`--restart no` 意味着应用不会自愈

容器一旦退出（OOM/异常）就永久停摆，而应用中心的状态判定只看 `docker ps` + PID 文件，
**可能仍显示"运行中"**，用户看到的是"应用活着但什么都干不了"。
→ 用 `--restart unless-stopped`，或在 `status` 分支里做真实 HTTP 探活。

### 坑 5：应用运行期间绝不能重启容器/应用

容器一停，**进行中的任务会被硬切断且没有任何收尾**，前端持有的旧 run_id 随即失效，
表现为「跑着跑着就没了 / 网页能开但状态全是错的」。
→ 调试期间要重启，先确认没有任务在跑。

### 坑 6：容器里查宿主 Docker 状态，别挂 `docker.sock`

挂 `docker.sock` 等于把 root 给容器。
→ 用「宿主只读 HTTP 代理 + 容器内假 docker 脚本」，见 `redroid-proxy/`。

## 9. 判断"某个容器是不是我起的"

**靠证据不靠记忆。** 三条互相印证：

1. **挂载路径**是否与你的 `docker run -v` 参数对得上
2. **RestartPolicy** 是否与 `--restart` 参数对得上
3. **创建时间**是否与 `info.log` 里的 `Starting container` 同秒

```bash
sudo docker inspect <容器> --format '{{json .Mounts}}'
sudo docker inspect <容器> --format '{{.HostConfig.RestartPolicy.Name}}'
sudo docker inspect <容器> --format '{{.State.StartedAt}}'
```

## 10. Windows 端开发的杂项

Git Bash（shim）里缺 `base64 / ls / head / mkdir / sleep / wc` 等命令，
跨机传文件建议走 Python + SSH + base64；`ssh` 用密码登录时注意：

- `sudo -S` **从 stdin 读密码** → 必须 `subprocess.run(..., input=(pw+"\n").encode())`。
  图省事写 `stdin=subprocess.DEVNULL` 会让远端 sudo 拿不到密码**死等到超时**。
- 加 `-o PreferredAuthentications=password -o PubkeyAuthentication=no -o NumberOfPasswordPrompts=1`，
  避免 Windows OpenSSH 先去试 publickey 白跑一轮。
