# 排障手册

面向"应用看起来活着但不好使"类问题。**核心原则：先分清是「被停过」还是「自己崩了」，再往下查。**

---

## 0. 三十秒体检

```bash
# ① 应用状态（返回 0 = running）
sudo appcenter-cli status maa-web

# ② 容器在不在、跑多久了、重启过几次、有没有被 OOM 杀
sudo docker inspect maa-web-test \
  --format '状态={{.State.Status}} 启动于={{.State.StartedAt}} 重启次数={{.RestartCount}} OOM={{.State.OOMKilled}} 退出码={{.State.ExitCode}}'

# ③ 网页通不通
curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://127.0.0.1:18000/

# ④ 应用自己的状态接口
curl -s http://127.0.0.1:18000/api/status
```

`/api/status` 正常长这样：

```json
{"state":"Idle","current_profile":null,"current_task":null,"total_tasks":0,"appended_tasks":0,"last_error":null}
```

运行中时 `state` 是 `Running`，会带 `current_profile` / `current_task`。

## 1. 判断"是谁把容器停了"

**这是最高频的误判来源**：应用没崩，是被外部停掉了。

```bash
sudo cat /vol1/@appdata/maa-web/info.log
```

这份日志由 `cmd/main` 写，`Stopping container ...` / `Starting container ...` 都带**秒级时间戳**。

```
2026-09-18 03:08:27 - Stopping container maa-web-test ...
2026-09-18 03:08:33 - Image id mismatch (...) -> will reload.
2026-09-18 03:08:33 - Removing stale image maa-web-control:local ...
2026-09-18 03:08:44 - Image loaded.
2026-09-18 03:08:47 - Container started: maa-web-test (0.0.0.0:18000)
```

拿着这个时间戳，去业务日志里找同一秒发生了什么，因果就清楚了。

另外两份：

```bash
sudo cat /vol1/@appdata/maa-web/install.log     # 安装/升级时镜像导入情况
sudo cat /vol1/@appdata/maa-web/uninstall.log   # 卸载时的容器清理情况
```

## 2. 判断"是不是 MaaCore 挂了"

MaaCore 的日志很关键的一点：**它是跨运行追加（append）的，历史不会被覆盖**。

```bash
# 看开头有没有 Process Start 横幅 —— 有，说明历史都还在
sudo docker exec maa-web-test head -c 900 /app/data/runtime/maa/debug/asst.log
```

期望类似：

```
[2026-09-17 22:38:50.798][TRC][Px1][Tx63168] -----------------------------
[2026-09-17 22:38:50.798][TRC][Px1][Tx63168] MaaCore Process Start
[2026-09-17 22:38:50.798][TRC][Px1][Tx63168] Version v6.17.5
[2026-09-17 22:38:50.798][TRC][Px1][Tx63168] Built at Sep  9 2026 21:29:43
[2026-09-17 22:38:50.798][TRC][Px1][Tx63168] User Dir /app/data/runtime/maa
```

### 2.1 拉任务链时间线（最有用的一招）

```bash
sudo docker exec maa-web-test sh -c \
  "grep -nE 'TaskChain(Start|Completed|Error)' /app/data/runtime/maa/debug/asst.log | tail -30"
```

读法：

| 现象 | 含义 |
|---|---|
| 有 `Start`、有 `Completed` | 该任务链正常跑完 |
| 有 `Start`、**没有** `Completed` | **被掐断**（容器/应用被停，或核心被杀） |
| `TaskChainError` | 任务链内部失败（接下去看第 3 节） |

MAA 的任务链顺序固定：`StartUp → Recruit → Infrast → Fight → Mall → Award`（按档案里启用情况）。

### 2.2 数错误

```bash
# 全部错误行
sudo docker exec maa-web-test sh -c \
  "grep '\[ERR\]' /app/data/runtime/maa/debug/asst.log | tail -20"

# 只看非 TRC 的（把海量模板匹配日志滤掉，量级从几万行降到几十行）
sudo docker exec maa-web-test sh -c \
  "sed -n '33620,33940p' /app/data/runtime/maa/debug/asst.log | grep -vE '\[TRC\]'"
```

常见的 `[ERR] skill has no recognition result` 属于**公招标签识别不出来**的正常告警，不是致命错。

## 3. 任务链失败时，去看"失败那一瞬间的截图"

**这是最高性价比的一招 —— 看图比读日志快十倍。**

MaaCore 会把出错时刻的原始截图落到 `debug/interface/`，文件名带毫秒时间戳：

```bash
sudo docker exec maa-web-test ls -la /app/data/runtime/maa/debug/interface/
```

```
-rwx------ 1 root root  770694 Sep 18 03:08 2026.09.18-03.08.27.838_raw.png
-rw-r--r-- 1 root root 1150957 Sep 18 04:01 2026.09.18-04.01.23.577_raw.png
```

**文件名里的时间戳 = 失败时刻**，直接和 2.1 的时间线对上。把图取回本地看：

```bash
# 容器内先缩小转 JPEG（1.1MB → 约 90KB，回传快）
sudo docker exec maa-web-test /app/.venv/bin/python -c "
from PIL import Image
im = Image.open('/app/data/runtime/maa/debug/interface/<文件名>').convert('RGB')
im.thumbnail((1000, 1000))
im.save('/tmp/shot.jpg', 'JPEG', quality=78)
print('OK')"

sudo docker exec maa-web-test base64 -w0 /tmp/shot.jpg
# 把输出粘到本地解码成 .jpg 打开
```

> ⚠️ 容器内的 Python 是 `/app/.venv/bin/python`，**不叫 `python`**（镜像里没有全局 `python`）。

## 4. 抓运行期状态

```bash
# 容器里的进程（能看到 uvicorn、adb fork-server、MaaTouch）
sudo docker exec maa-web-test ps -eo pid,ppid,etime,rss,cmd

# 有 <defunct> 说明应用没回收子进程（已知问题，见 BUGS.md #7）
```

```bash
# 数据目录长什么样
sudo docker exec maa-web-test find /app/data -maxdepth 3 \
  -printf '%y %10s %TY-%Tm-%Td %TH:%TM %p\n'
```

| 路径 | 内容 |
|---|---|
| `/app/data/profiles/*.json` | 任务档案 |
| `/app/data/tools_state.json` | 工具（公招识别等）状态 |
| `/app/data/runtime/maa/debug/asst.log` | MaaCore 引擎日志 |
| `/app/data/runtime/maa/debug/interface/` | 出错/关键时刻的原始截图 |
| `/app/data/runtime/maa/cache/avatars/` | 干员头像缓存 |

## 5. 容器日志怎么读

`docker logs` 里 90% 是前端的高频轮询，看不清事件。**把轮询滤掉**：

```bash
sudo docker logs maa-web-test 2>&1 \
  | grep -vE 'GET /api/(status|adb/devices) HTTP' \
  | grep -vE '(GET|POST) /api/logs' \
  | head -60
```

有意义的信号：`Started server process`（服务起来）、`Application startup complete`、
`WebSocket /api/events [accepted]`（前端连上了）、各种 `Requirement already satisfied`（`run.sh` 在装依赖）。

## 6. ADB / redroid 相关

```bash
# 容器内直接连一次
sudo docker exec maa-web-test adb connect <NAS_IP>:5555
sudo docker exec maa-web-test adb devices
# 期望：List of devices attached
#       <NAS_IP>:5555    device

# 看应用侧认为的连接状态
curl -s http://127.0.0.1:18000/api/adb/devices
```

`{"available":false,"message":"ADB 未配置"}` → 是**档案里还没填 ADB 地址**，去 *设置 → 连接* 里填。

### redroid 状态代理自测

```bash
# 宿主侧代理活着吗
curl -s 'http://172.17.0.1:18001/inspect?name=<redroid容器名>'
# 期望：{"ok": true, "status": "running", "running": true}

# 白名单外应被拒
curl -s 'http://172.17.0.1:18001/inspect?name=some-other-container'
# 期望：{"ok": false, "error": "container not allowed"}

# 容器内假 docker 是否生效
sudo docker exec maa-web-test docker inspect --format '{{.State.Status}}|{{.State.Running}}' <redroid容器名>
# 期望：running|true

# 假 docker 必须拒绝其他子命令
sudo docker exec maa-web-test docker ps
# 期望：非 0 退出
```

> 代理默认只允许**名字里含 `redroid`**（不区分大小写）的容器，见 `redroid_status_proxy.py` 里的 `ALLOW_PATTERNS`。

**排查不了就先看代理日志：**

```bash
sudo cat /vol1/@appdata/maa-web/redroid-proxy.log
# 或手工起的副本：
sudo cat /tmp/redroid-proxy.log
```

> ⚠️ 如果宿主机上**手工**起过一份代理，它会占住 18001 端口，
> 应用的 `ensure_redroid_proxy` 探活发现端口已被占用就会跳过启动自己的那份。
> 功能上等效，但**这份野进程不归应用管**，容易出玄学问题。排查时先确认：

```bash
ps -eo pid,etime,cmd | grep redroid_status_proxy | grep -v grep
```

## 7. 删掉重来

```bash
# 只重启应用（保留数据）
sudo appcenter-cli stop maa-web && sudo appcenter-cli start maa-web

# 彻底重来（镜像也删，下次启动会重新导入）
sudo appcenter-cli stop maa-web
sudo docker rm -f maa-web-test
sudo docker rmi -f maa-web-control:local

# 连用户数据一起清（不可恢复！）
sudo rm -rf /vol1/@appdata/maa-web/maa-data
```
